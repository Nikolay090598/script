# OpenWrt HomeStack 1.0-rc1

Единый интерактивный установщик и меню обслуживания.
Цель: OpenWrt с apk/firewall4, ARM64 или x86-64 при наличии нужных Docker-образов.
Это предварительная версия: синтаксис проверен, установка на физическом роутере не выполнялась.

## Старт

Передайте скрипт на роутер через SCP/SFTP. Если Bash отсутствует:

    apk update
    apk add bash

Затем в каталоге скрипта:

    bash openwrt-homestack.sh

Не запускайте через sh или ash. Все операции выполняются от root.
Не используйте chmod 777 для данных и секретов.

SHA-256 скрипта: bfeb6dd604e0aa36e4539416d9d942433d820adb6f036ceed54d99c1c1132929

## Обязательные условия

* Смонтированный диск. По умолчанию /mnt/sda1/homestack.
* Достаточно места для Docker, образов и временной сборки фронтенда.
* Проверьте Docker Root Dir: установка Docker на внутреннюю overlay-память может её заполнить.
* Диск и Docker data-root должны быть доступны ДО старта Docker при загрузке.
  Меню не перенастраивает fstab и глобальный порядок загрузки.
* SSH должен оставаться доступен во время замены веб-сервера.
* Изменения подтверждаются словом yes. Запуск скрипта сам по себе сервисы не устанавливает.

## Порядок на НОВОЙ системе

1. Пункт 1: BASE, LAN IPv4, WAN-зона, внешний IP/DNS, email, UID, адрес TeamSpeak.
2. Пункт 2: зависимости. Репозитории не подменяются; apk del/upgrade/--force не вызываются.
3. Пункт 3: место, сокеты, контейнеры, Docker Root Dir.
4. Установите TeamSpeak. Получите privilege key в логах. Подключитесь локально,
   примените ключ, задайте пароль сервера и проверьте гостевые права.
5. Установите MusicBot. Пароль сервера вводится скрыто. Адрес для нового host-TS6:
   LAN_IP:9987, не Docker-имя ts6-server.
6. Установите Mumble/RustDesk/TorrServer/Beszel по необходимости.
7. Настройте HTTPS-сайты, затем отдельно откройте WAN443.
8. Остальные WAN-порты включайте по одному после локальной проверки защиты.
9. Проверьте доступ с МОБИЛЬНОГО интернета и перезагрузку в удобное время.

## Текущая работающая система

Новые установки ОТКАЗЫВАЮТСЯ заменять существующие контейнеры и непустые каталоги.
Автоматической миграции существующих volumes, Env, портов и сетей нет.
Можно использовать статус, логи, явное обслуживание конкретного контейнера и Caddy
с вручную указанным backend-адресом.
Правила открытия WAN для TS/Mumble/RustDesk ограничены контейнерами с меткой HomeStack;
они не предназначены для управления прежними Docker-публикациями.

Текущий lighttpd сохраняется без перезаписи. Новый Caddy не требует отключать его порт 80.
Для существующего TorrServer на :::8090 публичный HTTPS-мастер откажется продолжать,
пока backend не будет привязан только к 127.0.0.1:8090. Он не пересоздаёт его сам.
Это намеренный защитный барьер, а не ошибка установщика.

## HTTPS и DNS

Для каждого сайта задаётся отдельный полный поддомен. Один купленный домен достаточен.
A-записи направьте на реальный внешний IPv4. Удалите ошибочные AAAA.
Не используйте CDN-проксирование для TLS-ALPN в этом варианте: нужен DNS-only.
TCP443 должен напрямую доходить до Caddy. Если перед OpenWrt есть ещё NAT,
на нём нужен соответствующий проброс. Скрипт не управляет чужим модемом и DNS.

Caddy использует TLS-ALPN-01. HTTP challenge и автоматический HTTP redirect выключены:
порт 80 остаётся у lighttpd. HTTP/3 не включён; хватает TCP443.
Получение и продление серверных сертификатов выполняет Caddy. Хранилище сохраняется на диске.
Сайты добавляются по одному. Удаление сайта: вручную удалить соответствующий .caddy
из каталога https/sites и выполнить caddy reload; автоматического пункта удаления нет.
Административный API Caddy слушает только 127.0.0.1:2019.

### MusicBot

Для публичного сайта требуется клиентский сертификат mTLS в дополнение к штатному UID/API-токену.
Это предотвращает анонимный вход к сайту и не занимает API-заголовок Authorization.
Скрипт создаёт client.p12 в client-pki, защищённый отдельным паролем.
Импортируйте его в браузер/ОС. На разных устройствах поддержка импорта может отличаться.
Без клиентского сертификата HTTPS-соединение к этому сайту должно отвергаться.
Клиентский сертификат действует 365 дней; автоматического продления и CRL/отзыва нет.
При компрометации нужно сменить клиентский CA и профиль. CA private key НЕ монтируется в Caddy.
Клиентский p12, export-pass.txt и ключи — секреты, не отправляйте их в чат.

### TorrServer

Публичный режим: native HTTP Basic auth на всех запросах плюс тот же логин/пароль
на Caddy. Нет второго независимого набора credentials. Backend — только loopback.
При публикации проверяется 401 без credentials и успешный ответ с credentials.
Все stream-пути остаются защищёнными. Публичного auth-bypass для видео нет.
Применяется flush_interval -1 для потоков.
VLC и Next Player нужно проверять ОТДЕЛЬНО: передача пароля из приложения не гарантируется.
Если клиент не передаёт auth, используйте VPN, а не открытые потоки.

VPN-режим: сервер на LAN:8090 без HTTP-пароля, доступный доверенным LAN/VPN-клиентам.
В публичный Caddy этот режим не публикуется. Это не режим изоляции от других LAN-устройств.

### Beszel

Устанавливается HUB, не agent. Прежде чем публиковать сайт, создайте аккаунт локально.
Штатная авторизация сохраняется, WebSocket проксируется Caddy.
AUTO_LOGIN запрещён мастером, но настройки регистрации/OIDC/доверенных заголовков
нужно проверить самостоятельно. Мастер не является аудитом всех настроек PocketBase.
Не размещайте неинициализированный Hub в интернете.

### LuCI

Отдельный пункт сайта, отдельный пароль Caddy и затем штатная LuCI-сессия.
Прокси удаляет свой Authorization перед отправкой в LuCI; пароль LuCI вводится штатно.
Встроенного MFA/лимитера попыток входа/геоблокировки здесь нет.
VPN предпочтительнее публичной админки. Нельзя обещать защиту от всех атак и DDoS.
Не публикуйте напрямую WAN80, ttyd, SSH или ubus.

## lighttpd без удаления Nginx

Если lighttpd уже запущен — мастер ничего не переписывает.
На новой системе схема: lighttpd (LAN80) -> uhttpd (127.0.0.1:18088) для CGI/RPC.
Это сознательная совместимость с родным CGI/RPC OpenWrt, а не удаление uhttpd.
Nginx, его пакеты и LuCI-зависимости не удаляются.
Сначала тест на LAN18080: проверьте вход, страницы, сохранение, загрузку файлов,
терминал и специфические функции вашей кастомной прошивки.
Лишь после подтверждения Nginx останавливается и выключается из автозапуска.
При переключении действует независимый таймер отката 180 секунд; подтверждение KEEP.
Это таймер в работающей системе, он НЕ является транзакционным откатом при обесточивании.
Не перезагружайте и не обновляйте роутер во время переключения.
При прерванной подготовке мастер не перезаписывает уже созданную helper-службу;
повторный запуск требует ручной проверки результатов прошлого запуска.

## WireGuard

Нужно заранее поставить wireguard-tools и соответствующий ядру kmod-wireguard
из репозиториев своей прошивки. Не применяйте --force к модулям ядра.
При необходимости: apk add wireguard-tools kmod-wireguard luci-proto-wireguard.

Один доверенный административный профиль: 10.77.77.2, сервер 10.77.77.1/24.
Убедитесь, что подсеть не пересекается с другими сетями.
Разрешены TCP80/8090/8091/58913 только на LAN-адресе роутера; пересылка во весь LAN запрещена.
Профиль включает доступ к LuCI: НЕ выдавайте его другу только для просмотра фильмов.
Несколько раздельных VPN-профилей с разными правами в rc1 не реализованы.
Конфиг client.conf содержит закрытый ключ; один профиль — одно устройство.
Публичный вход только UDP51820. IPv6-стек не выключается.

## Firewall и IPv6

IPv6 в системе/LAN НЕ отключается. Для публичных host-сервисов HomeStack
открываются только правила IPv4; для их портов добавляется запрет WAN IPv6.
Скрипт требует WAN input DROP/REJECT и отсутствие несохранённых firewall-изменений.
Сохраняет предыдущий firewall и делает fw4 check перед применением.

ВАЖНО: это НЕ полный аудит чужих redirect/ACCEPT, Docker DNAT или других WAN-зон.
INPUT-правила не гарантируют блокировку произвольных существующих bridge-публикаций.
LAN IP binding тоже не заменяет полноценную внешнюю проверку.
Не используйте мастер как доказательство отсутствия обхода через ваши прежние пробросы.

## Безопасность и сохранность

* По умолчанию новые public host-сервисы сначала закрыты в WAN.
* Для TS пароль задаётся клиентом локально; мастер спрашивает подтверждение перед открытием.
* RustDesk использует key enforcement, но это не замена паролю/подтверждению удалённого ПК.
* Mumble требует разные пароли входа/SuperUser. Сверьте сертификат при первом входе.
* До установки можно выбрать точные версии или image@sha256 через пункт образов.
* latest/master используются по умолчанию: воспроизводимость без закрепления не гарантируется.
* Для старого фронтенда бота используется временный Node16. Это EOL build-инструмент.
  Сборка выполняет upstream npm scripts; это цепочка поставки, требующая доверия.
* Нет автоматического обновления образов. Нет автоматического удаления контейнеров.
* unless-stopped не запускает после ребута ранее вручную остановленный контейнер.
* Автостарт контейнера не означает автозапуск музыки.
* Логи могут содержать административные ключи. Не пересылайте их без проверки.
* Пароли есть в защищённых файлах/Env. Root и доступ к Docker дают доступ к ним.

## Резервная копия

Пункт 16 останавливает только работающие контейнеры с меткой HomeStack, сохраняет BASE,
конфиги роутера и состояние, затем запускает их обратно. Это краткий перерыв сервисов.
Музыка, build и предыдущие backup-архивы исключены. Existing installations вне BASE
не архивируются. Базы чужих работающих сервисов в консистентность не включены.
Копия содержит секреты; обязательно хранить её ещё и на другом устройстве.
Автоматического восстановления поверх живой системы нет — это исключает случайную
перезапись сети/ключей. Используйте архив для контролируемого восстановления.

## Что проверено при подготовке

Bash syntax (bash -n), TOML конфигурации ядра MusicBot и XML NLog.
Не проверено на физической OpenWrt: Docker image pull для ARM64, запуск сервисов,
все LuCI CGI/RPC-функции, внешняя выдача сертификатов, работа VLC/Next Player и reboot.
Название rc1 отражает это ограничение. Начинайте с диагностики и резервных копий.
